    Tuần 3 · Ngày 5 · Repository có validation và errors¶

    Mục tiêu: Kết hợp validation, custom errors và repository có thao tác ghi thành một data layer đáng tin cậy, kèm kiểm thử đường lỗi.
    Thời lượng: 90–120 phút

    Khái niệm: error propagation, validation, duplicate ID, repository mutation, test error paths, checkpoint tuần 3

    • Đã đọc xong
    • Đã làm hết bài tập

    1. Mục tiêu và thiết kế¶

    Ở tuần 2, repository chỉ đọc dữ liệu. Giờ ta thêm thao tác ghi (add, update, remove) và để chúng thất bại có kiểm soát: ID rỗng, năm sai, ID trùng, không tìm thấy. Mọi quy tắc nghiệp vụ tập trung ở một chỗ, người gọi chỉ cần xử lý lỗi có tên.

    Quyết định thiết kế: • Lỗi là enum VehicleError (bài 4), conform LocalizedError. • Validation tách thành hàm riêng, dễ test. • Repository là final class vì có trạng thái thay đổi và được chia sẻ (cùng một kho dữ liệu cho nhiều nơi). • Contract dùng throws cho thao tác ghi; thao tác đọc có thể trả Optional.

    2. Contract và model¶

    Contract khai báo throws ở các thao tác có thể thất bại. Model giữ nguyên là struct. Lưu ý cách phân vai: validate kiểm tra dữ liệu, repository kiểm tra quy tắc liên quan trạng thái (trùng ID, tồn tại).

    import Foundation

struct Vehicle: Identifiable, Equatable {
    let id: String
    var make: String
    var model: String
    var year: Int
}

enum VehicleError: Error, Equatable, LocalizedError {
    case emptyID
    case emptyName
    case invalidYear(Int)
    case duplicateID(String)
    case notFound(String)

    var errorDescription: String? {
        switch self {
        case .emptyID:             return "ID không được để trống"
        case .emptyName:           return "Hãng và model không được để trống"
        case .invalidYear(let y):  return "Năm \(y) không hợp lệ (1990–2100)"
        case .duplicateID(let id): return "ID \(id) đã tồn tại"
        case .notFound(let id):    return "Không tìm thấy xe \(id)"
        }
    }
}

protocol VehicleRepository {
    func getAll() -> [Vehicle]
    func find(id: String) -> Vehicle?
    func add(_ vehicle: Vehicle) throws
    func update(_ vehicle: Vehicle) throws
    func remove(id: String) throws
}

    3. Cài đặt in-memory có validation¶

    Validation là hàm thuần (không phụ thuộc trạng thái) nên rất dễ kiểm thử. Repository gọi validation trước, rồi mới kiểm tra các quy tắc liên quan tới dữ liệu đang có. Dùng guard để thoát sớm và ném lỗi đúng case.

    Lưu ý: final class cho phép thuộc tính private var vehicles thay đổi từ method mà không cần mutating. Nếu về sau có nhiều luồng truy cập đồng thời, bạn sẽ cần actor (tuần 7).

    enum VehicleValidator {
    static func validate(_ v: Vehicle) throws {
        guard !v.id.trimmingCharacters(in: .whitespaces).isEmpty else { throw VehicleError.emptyID }
        guard !v.make.isEmpty, !v.model.isEmpty else { throw VehicleError.emptyName }
        guard (1990...2100).contains(v.year) else { throw VehicleError.invalidYear(v.year) }
    }
}

final class InMemoryVehicleRepository: VehicleRepository {
    private var vehicles: [Vehicle]
    init(vehicles: [Vehicle] = []) { self.vehicles = vehicles }

    func getAll() -> [Vehicle] { vehicles }
    func find(id: String) -> Vehicle? { vehicles.first { $0.id == id } }

    func add(_ vehicle: Vehicle) throws {
        try VehicleValidator.validate(vehicle)
        guard find(id: vehicle.id) == nil else { throw VehicleError.duplicateID(vehicle.id) }
        vehicles.append(vehicle)
    }

    func update(_ vehicle: Vehicle) throws {
        try VehicleValidator.validate(vehicle)
        guard let index = vehicles.firstIndex(where: { $0.id == vehicle.id }) else {
            throw VehicleError.notFound(vehicle.id)
        }
        vehicles[index] = vehicle
    }

    func remove(id: String) throws {
        guard let index = vehicles.firstIndex(where: { $0.id == id }) else {
            throw VehicleError.notFound(id)
        }
        vehicles.remove(at: index)
    }
}

    4. Dùng repository và xử lý lỗi ở nơi gọi¶

    Ở nơi gọi (sau này là ViewModel), mỗi thao tác ghi nằm trong do-catch. Thông báo cho người dùng lấy từ error.localizedDescription nhờ LocalizedError. Lỗi nên được chuyển thành trạng thái UI (tuần 5, 6), không chỉ print.

    Chú ý tính nhất quán: nếu thao tác thất bại, trạng thái của repository không được thay đổi một phần (atomicity đơn giản). Ở trên, validation và kiểm tra trùng xảy ra trước khi append, nên lỗi không để lại dữ liệu nửa vời.

    let repo: VehicleRepository = InMemoryVehicleRepository()

let inputs = [
    Vehicle(id: "V001", make: "Toyota", model: "Camry", year: 2024),
    Vehicle(id: "V001", make: "Honda", model: "Civic", year: 2022),   // trùng ID
    Vehicle(id: "", make: "Ford", model: "Focus", year: 2021),        // ID rỗng
    Vehicle(id: "V003", make: "Kia", model: "Seltos", year: 1980)     // năm sai
]

for item in inputs {
    do {
        try repo.add(item)
        print("OK \(item.id)")
    } catch {
        print("Lỗi: \(error.localizedDescription)")
    }
}
print(repo.getAll().count)   // 1

    5. Kiểm thử đường lỗi¶

    Đường lỗi cũng là hành vi cần kiểm thử, thậm chí quan trọng hơn đường thành công. Với Equatable trên enum lỗi, bạn so sánh trực tiếp. Tuần 6 bạn sẽ dùng XCTest chính thức; bây giờ có thể dùng assert/hàm kiểm tra đơn giản trong một file chạy thử.

    Danh sách case nên có: thêm xe hợp lệ; thêm trùng ID; ID rỗng; năm sai; update xe không tồn tại; remove xe không tồn tại; sau lỗi thì dữ liệu không đổi.

    func expect(_ condition: Bool, _ message: String) {
    print(condition ? "PASS: \(message)" : "FAIL: \(message)")
}

func expectError(_ expected: VehicleError, _ body: () throws -> Void, _ message: String) {
    do {
        try body()
        print("FAIL: \(message) (không có lỗi)")
    } catch let error as VehicleError {
        expect(error == expected, message)
    } catch {
        print("FAIL: \(message) (sai loại lỗi)")
    }
}

let r = InMemoryVehicleRepository()
try r.add(Vehicle(id: "V1", make: "A", model: "B", year: 2020))

expectError(.duplicateID("V1"), { try r.add(Vehicle(id: "V1", make: "A", model: "B", year: 2020)) }, "trùng ID")
expectError(.emptyID, { try r.add(Vehicle(id: "", make: "A", model: "B", year: 2020)) }, "ID rỗng")
expectError(.invalidYear(1900), { try r.add(Vehicle(id: "V2", make: "A", model: "B", year: 1900)) }, "năm sai")
expectError(.notFound("V9"), { try r.remove(id: "V9") }, "xóa xe không có")
expect(r.getAll().count == 1, "dữ liệu không đổi sau các lỗi")

    6. Lỗi thường gặp và đánh đổi¶

    1. Validation rải rác ở View, ViewModel và repository: quy tắc không nhất quán. Hãy gom về một nơi.
    2. Ném lỗi sau khi đã sửa một phần dữ liệu: để lại trạng thái hỏng.
    3. Dùng NSError hoặc một kiểu lỗi chung chung cho mọi trường hợp: mất khả năng switch đầy đủ theo từng case nghiệp vụ.
    4. Chỉ kiểm thử đường thành công.
    5. Để lỗi kỹ thuật (mạng, DB) lẫn với lỗi nghiệp vụ trong cùng enum mà không phân loại: UI khó quyết định hiển thị gì.
    6. Dùng try!/try? ở repository để "cho gọn".

    Đánh đổi: một lớp VehicleValidator riêng thêm một chút code, nhưng có thể dùng lại ở form (tuần 5) để báo lỗi từng ô ngay khi người dùng nhập.

    7. Tóm tắt và checkpoint tuần 3¶

    • Repository có thao tác ghi dùng throws và enum lỗi nghiệp vụ. • Validation là hàm thuần, kiểm tra trước; trạng thái chỉ đổi khi mọi kiểm tra đã qua. • Thông báo thân thiện qua LocalizedError. • Kiểm thử cả đường lỗi, bảo đảm dữ liệu không đổi khi lỗi.

    Checklist trước khi sang tuần 4: ☐ Giải thích được ARC và vì sao deinit không chạy khi có retain cycle. ☐ Biết chọn weak, unowned, [weak self] đúng chỗ. ☐ Phân biệt Optional, throws và crash. ☐ Viết custom error enum và do-catch theo từng case. ☐ Có bộ kiểm tra cho repository: ít nhất 5 case lỗi.

    Bài tập¶

    Tự làm trước, rồi mới mở gợi ý / đáp án.

    Bài 1 — Thêm xe và xử lý trùng ID¶

    Dùng InMemoryVehicleRepository ở trên, thêm hai xe cùng id. Bắt lỗi và in thông báo từ localizedDescription. Dữ liệu sau đó có mấy xe?

    Gợi ý Xe thứ hai làm add ném duplicateID trước khi append.
    Đáp án 
    let repo = InMemoryVehicleRepository()
let a = Vehicle(id: "V1", make: "Toyota", model: "Camry", year: 2024)
let b = Vehicle(id: "V1", make: "Honda", model: "Civic", year: 2022)

do {
    try repo.add(a)
    try repo.add(b)
} catch {
    print(error.localizedDescription)   // ID V1 đã tồn tại
}
print(repo.getAll().count)              // 1
    **Giải thích:** Việc kiểm tra trùng xảy ra trước khi `append` nên lỗi không để lại dữ liệu hỏng; còn đúng một xe.

    Bài 2 — Thêm thao tác update¶

    Viết test: update một xe không tồn tại phải ném notFound, còn xe tồn tại thì dữ liệu được thay đổi và find(id:) trả về giá trị mới.

    Gợi ý Dùng firstIndex(where:) và gán vehicles[index].
    Đáp án 
    let repo = InMemoryVehicleRepository()
try repo.add(Vehicle(id: "V1", make: "Toyota", model: "Camry", year: 2020))

try repo.update(Vehicle(id: "V1", make: "Toyota", model: "Camry", year: 2024))
print(repo.find(id: "V1")?.year ?? 0)     // 2024

do {
    try repo.update(Vehicle(id: "V9", make: "A", model: "B", year: 2020))
} catch VehicleError.notFound(let id) {
    print("Không có \(id)")                // Không có V9
} catch {
    print("Lỗi khác")
}
    **Giải thích:** `update` vừa validate dữ liệu mới vừa kiểm tra tồn tại; mỗi lỗi có một case riêng để nơi gọi xử lý.

    Bài 3 — Atomicity khi lỗi¶

    Giải thích vì sao thứ tự "validate → kiểm tra trùng → append" quan trọng. Điều gì xảy ra nếu bạn append trước rồi mới kiểm tra trùng?

    Gợi ý Nghĩ tới trạng thái của repository khi lỗi bị ném.
    Đáp án 
    // Sai: sửa dữ liệu trước, kiểm tra sau
func addWrong(_ v: Vehicle) throws {
    vehicles.append(v)                        // dữ liệu đã thay đổi
    guard find(id: v.id) == nil else {        // luôn thấy chính nó -> logic sai
        throw VehicleError.duplicateID(v.id)
    }
}

// Đúng: kiểm tra mọi điều kiện, rồi mới thay đổi
func add(_ v: Vehicle) throws {
    try VehicleValidator.validate(v)
    guard find(id: v.id) == nil else { throw VehicleError.duplicateID(v.id) }
    vehicles.append(v)
}
    **Giải thích:** Nếu append trước, lỗi được ném nhưng dữ liệu đã bị sửa (trạng thái hỏng) và kiểm tra trùng còn luôn sai. Quy tắc: kiểm tra xong hết rồi mới thay đổi.

    Bài 4 — Phân loại lỗi¶

    Phân loại các tình huống sau vào: Optional, throws, hay crash. (a) tìm xe theo ID không có; (b) thêm xe có năm không hợp lệ; (c) truy cập vehicles[10] khi chỉ có 3 xe do bug; (d) parse JSON sai định dạng từ server.

    Gợi ý Hỏi: có phải tình huống bình thường, lỗi phục hồi được, hay lỗi lập trình?
    Đáp án 
    // (a) Optional: "không tìm thấy" là kết quả bình thường.
func find(id: String) -> Vehicle?

// (b) throws: dữ liệu sai từ người dùng, cần báo lý do.
func add(_ v: Vehicle) throws

// (c) crash (index out of range): bug lập trình, không nên cố "bắt".

// (d) throws: dữ liệu bên ngoài không đáng tin.
let model = try JSONDecoder().decode(Vehicle.self, from: data)
    **Giải thích:** Optional cho thiếu giá trị thông thường, `throws` cho lỗi phục hồi và cần lý do, crash cho vi phạm bất biến của chương trình. Chọn đúng giúp API rõ ràng.
