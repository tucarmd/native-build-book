    Tuần 3 · Ngày 2 · Retain cycle giữa các object¶

    Mục tiêu: Nhận diện object graph có chu trình tham chiếu mạnh và sửa bằng cách thiết kế lại quan hệ sở hữu.
    Thời lượng: 75–90 phút

    Khái niệm: retain cycle, object graph, ownership, weak reference, parent-child, delegate

    • Đã đọc xong
    • Đã làm hết bài tập

    1. Retain cycle là gì¶

    Retain cycle xảy ra khi hai (hoặc nhiều) class instance giữ strong reference lẫn nhau, trực tiếp hoặc qua một chuỗi. Mỗi bên giữ bên kia sống, nên bộ đếm của cả hai không bao giờ về 0 dù không còn ai bên ngoài dùng. Kết quả là memory leak: bộ nhớ bị chiếm mãi cho đến khi app thoát.

    Triệu chứng điển hình: deinit không bao giờ chạy, bộ nhớ app tăng dần khi bạn lặp đi lặp lại thao tác (vào/ra một màn hình), dữ liệu cũ vẫn bị cập nhật dù màn hình đã đóng.

    final class Owner {
    let name: String
    var device: Device?
    init(name: String) { self.name = name }
    deinit { print("Owner \(name) freed") }
}

final class Device {
    let id: String
    var owner: Owner?                 // strong: tạo vòng tham chiếu
    init(id: String) { self.id = id }
    deinit { print("Device \(id) freed") }
}

var owner: Owner? = Owner(name: "An")
var device: Device? = Device(id: "D1")
owner?.device = device
device?.owner = owner

owner = nil
device = nil
// KHÔNG in "freed": Owner giữ Device, Device giữ Owner -> rò rỉ

    2. Cách phát hiện¶

    Có ba cách, từ rẻ đến đầy đủ: 1. Đặt print trong deinit và thử đóng/mở màn hình: nếu không thấy in ra, đang rò rỉ. 2. Xcode Debug Memory Graph (nút ba hình tròn trên thanh debug): hiển thị object còn sống và các mũi tên tham chiếu; instance màn hình đã đóng nhưng còn tồn tại là dấu hiệu. 3. Instruments > Leaks/Allocations (tuần 8).

    Các nơi dễ rò rỉ nhất: quan hệ cha ↔ con, delegate, closure lưu trong thuộc tính (callback, handler), observer/timer, và ViewModel giữ closure tham chiếu lại chính nó.

    3. Phá vòng bằng weak¶

    Nguyên tắc: trong một cặp quan hệ, chỉ một chiều là sở hữu (strong); chiều còn lại là tham chiếu quan sát không sở hữu, khai báo weak. Hỏi: "bên nào quyết định vòng đời của bên kia?" Bên đó giữ strong. Ví dụ Owner sở hữu Device, còn Device chỉ cần biết ai là chủ nên dùng weak var owner.

    weak có ba đặc điểm: (1) phải là var và kiểu Optional; (2) không tăng reference count; (3) tự động thành nil khi instance bị giải phóng. Vì vậy bạn luôn phải xử lý Optional khi dùng.

    final class Owner {
    let name: String
    var device: Device?
    init(name: String) { self.name = name }
    deinit { print("Owner \(name) freed") }
}

final class Device {
    let id: String
    weak var owner: Owner?            // không giữ owner
    init(id: String) { self.id = id }
    deinit { print("Device \(id) freed") }
}

var owner: Owner? = Owner(name: "An")
var device: Device? = Device(id: "D1")
owner?.device = device
device?.owner = owner

owner = nil                           // "Owner An freed"
print(device?.owner == nil)           // true: weak tự về nil
device = nil                          // "Device D1 freed"

    4. Delegate pattern và weak¶

    Delegate là mẫu rất phổ biến của UIKit/CoreBluetooth: object A giữ B làm delegate để B nhận thông báo. Nếu B cũng giữ A (thường vậy) thì tạo vòng. Quy ước của Apple: thuộc tính delegate luôn là weak. Để dùng weak với protocol, protocol phải giới hạn cho class bằng AnyObject.

    Nếu bạn tự viết delegate, hãy tuân theo quy ước này: người sở hữu (thường là view controller/manager) giữ đối tượng làm việc bằng strong; đối tượng làm việc giữ delegate bằng weak.

    protocol ScannerDelegate: AnyObject {
    func scanner(_ scanner: Scanner, didFind name: String)
}

final class Scanner {
    weak var delegate: ScannerDelegate?       // weak để tránh vòng
    func found(_ name: String) { delegate?.scanner(self, didFind: name) }
    deinit { print("Scanner freed") }
}

final class ScreenModel: ScannerDelegate {
    let scanner = Scanner()                   // sở hữu scanner (strong)
    init() { scanner.delegate = self }
    func scanner(_ scanner: Scanner, didFind name: String) { print("Found \(name)") }
    deinit { print("ScreenModel freed") }
}

var model: ScreenModel? = ScreenModel()
model?.scanner.found("ELM327")
model = nil        // cả hai deinit đều chạy

    5. So sánh với JavaScript/Angular¶

    Trong JS, hai object tham chiếu nhau là bình thường vì GC theo dõi tính "reachable từ root", nên cả cặp bị thu hồi khi không còn ai tới được. ARC chỉ đếm, không phân tích đồ thị, nên vòng tham chiếu luôn là lỗi thiết kế cần chủ động xử lý.

    Tương tự Angular: subscription không unsubscribe làm component bị giữ sống. Với ARC, nguyên nhân thường là closure/observer/timer giữ object. Cách nghĩ giống nhau: ai giữ ai, và phải có điểm cắt.

    6. Lỗi thường gặp¶

    1. Quan hệ hai chiều (cha ↔ con, A ↔ B) mà cả hai đều strong.
    2. Quên weak cho delegate.
    3. Dùng weak cho quan hệ mà thực ra cần sở hữu: đối tượng biến mất bất ngờ (về nil) vì chẳng ai giữ nó.
    4. Khai báo protocol delegate không có : AnyObject nên không dùng được weak.
    5. Nghĩ rằng chỉ cần "đặt nil ở cuối" là đủ: vòng tham chiếu cần cắt bằng thiết kế, không phải dọn tay.
    6. Không kiểm tra bằng deinit/Memory Graph rồi kết luận "chắc không rò".

    7. Tóm tắt¶

    • Retain cycle: hai bên giữ nhau bằng strong, nên không bên nào được giải phóng. • Xác định ai sở hữu ai: chiều sở hữu dùng strong, chiều quan sát dùng weak. • weak là var Optional, không tăng bộ đếm và tự thành nil. • Delegate luôn weak; protocol của delegate giới hạn AnyObject. • Kiểm tra bằng deinit và Debug Memory Graph.

    Bài tập¶

    Tự làm trước, rồi mới mở gợi ý / đáp án.

    Bài 1 — Tìm vòng tham chiếu¶

    Cho Owner có var device: Device? và Device có var owner: Owner? (cả hai strong). Sau khi tạo và gán chéo rồi đặt cả hai biến về nil, deinit có chạy không? Sửa bằng một từ khóa.

    Gợi ý Chọn chiều "quan sát" (không sở hữu) để đánh dấu weak.
    Đáp án 
    final class Owner {
    var device: Device?
    deinit { print("Owner freed") }
}
final class Device {
    weak var owner: Owner?     // thêm weak
    deinit { print("Device freed") }
}

var o: Owner? = Owner()
var d: Device? = Device()
o?.device = d
d?.owner = o
o = nil
d = nil      // cả hai deinit đều chạy
    **Giải thích:** Trước khi sửa không có `deinit` nào chạy vì mỗi bên giữ bên kia. Thêm `weak` ở chiều Device → Owner phá vòng: Owner chỉ còn Device giữ và Device giữ bởi Owner nhưng không có vòng.

    Bài 2 — Vì sao weak là Optional?¶

    Giải thích vì sao weak var owner: Owner? bắt buộc là var và Optional. Viết đoạn chứng minh owner tự về nil.

    Gợi ý Giá trị phải thay đổi được khi instance bị giải phóng.
    Đáp án 
    final class Owner { deinit { print("Owner freed") } }
final class Device { weak var owner: Owner? }

var o: Owner? = Owner()
let d = Device()
d.owner = o
print(d.owner != nil)   // true
o = nil                 // "Owner freed"
print(d.owner == nil)   // true: ARC tự gán nil
    **Giải thích:** ARC phải ghi `nil` vào tham chiếu weak khi instance bị giải phóng, nên cần `var` và kiểu Optional để biểu diễn "không còn đối tượng".

    Bài 3 — Delegate an toàn¶

    Viết protocol DataSourceDelegate và class DataSource có thuộc tính delegate. Giải thích vì sao protocol cần AnyObject và thuộc tính cần weak.

    Gợi ý weak chỉ áp dụng cho tham chiếu tới class.
    Đáp án 
    protocol DataSourceDelegate: AnyObject {
    func dataDidChange()
}

final class DataSource {
    weak var delegate: DataSourceDelegate?
    func update() { delegate?.dataDidChange() }
}

final class Screen: DataSourceDelegate {
    let source = DataSource()
    init() { source.delegate = self }
    func dataDidChange() { print("refresh") }
}
    **Giải thích:** `AnyObject` giới hạn protocol cho class nên mới dùng được `weak`. `Screen` giữ `DataSource` (strong), `DataSource` chỉ giữ `Screen` yếu nên không có vòng.
