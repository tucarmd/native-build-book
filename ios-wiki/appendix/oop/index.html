    Phụ lục · OOP trong Swift: bốn trụ cột, và khi nào không nên dùng¶

    Mục tiêu: Tổng hợp hướng đối tượng trong Swift (đóng gói, kế thừa, đa hình, trừu tượng), so sánh với TypeScript/Java/Kotlin và cách kết hợp với functional và protocol-oriented programming.
    Thời lượng: Tham khảo khi cần

    Khái niệm: OOP, Encapsulation, Inheritance, Polymorphism, Abstraction, Composition over inheritance, Protocol-oriented, SOLID

    • Đã đọc xong
    • Đã làm hết bài tập

    1. Swift đứng ở đâu trong thế giới OOP¶

    Swift là ngôn ngữ đa mô hình: hỗ trợ hướng đối tượng (class, kế thừa), hướng protocol, functional (closure, hàm bậc cao) và hướng giá trị (struct, enum). Apple mô tả triết lý là "value types first, protocols over inheritance": ưu tiên kiểu giá trị và protocol, dùng class khi thật sự cần identity hoặc kế thừa.

    Bốn trụ cột của OOP và cách Swift hiện thực: • Đóng gói (encapsulation): access control (private, fileprivate, internal, public, open), private(set). • Kế thừa (inheritance): chỉ class, đơn kế thừa, có override, super, final. • Đa hình (polymorphism): qua kế thừa, qua protocol, qua generics. • Trừu tượng (abstraction): protocol thay cho abstract class, associatedtype, some/any.

    Phần lớn app iOS vẫn dùng class nhiều, vì UIKit/Foundation (UIViewController, NSObject, Timer) xây dựng trên class và delegate. Nhưng code nghiệp vụ hiện đại của bạn nên thiên về struct, enum và protocol.

    2. Class và object: nhắc lại những khác biệt cốt lõi với struct¶

    • Reference type: nhiều biến cùng trỏ một instance; có identity (===). • Có vòng đời quản lý bởi ARC và deinit; có nguy cơ retain cycle (tuần 3). • Có kế thừa; struct/enum thì không. • Phải tự viết initializer (không có memberwise init tự sinh), tuân theo quy tắc khởi tạo hai pha. • let với class chỉ cố định tham chiếu, thuộc tính var bên trong vẫn sửa được. • Method không final dùng dynamic dispatch.

    Có class func (kiểu method mà subclass override được) và static func (không override được). self trong class là tham chiếu tới chính instance, Self (chữ hoa) là kiểu của nó.

    final class Counter {
    private(set) var value = 0
    func increment() { value += 1 }
    deinit { print("Counter freed with \(value)") }
}

let a = Counter()
let b = a                 // cùng một đối tượng
b.increment()
print(a.value, a === b)   // 1 true

struct Point { var x = 0 }
var p1 = Point()
var p2 = p1               // bản sao độc lập
p2.x = 9
print(p1.x, p2.x)         // 0 9

    3. Đóng gói (encapsulation): các mức truy cập¶

    Đóng gói nghĩa là che chi tiết cài đặt và chỉ công khai giao diện cần thiết. Swift có năm mức, từ rộng tới hẹp: • open: ngoài module vẫn kế thừa và override được (chỉ class, dùng cho framework). • public: ngoài module dùng được nhưng không kế thừa/override. • internal (mặc định): trong cùng module (target). • fileprivate: trong cùng file. • private: trong khai báo bao quanh và extension của nó trong cùng file.

    Swift không có protected. Muốn "con được dùng, bên ngoài thì không" thì đặt hai lớp cùng file và dùng fileprivate, hoặc thiết kế lại qua protocol/composition.

    Công cụ hay dùng: private(set) (đọc rộng, ghi hẹp), private init (chặn tạo instance tùy ý, hợp với singleton hoặc factory), private extension (gom helper nội bộ). Mức truy cập của một thành phần không được rộng hơn kiểu chứa nó và kiểu của tham số/giá trị trả về.

    Quy tắc thực dụng: mặc định để hẹp nhất (private), mở rộng khi có lý do. Dự án chỉ có một module thì hiếm khi cần public/open.

    public class BluetoothSession {
    public let id: String                          // đọc được từ module khác
    public private(set) var state: State = .idle   // ngoài module chỉ đọc
    private var retryCount = 0                     // chỉ trong lớp (và extension cùng file)
    fileprivate var debugLog: [String] = []        // cả file dùng được
    var isActive: Bool { state != .idle }          // internal (mặc định)

    public enum State { case idle, connecting, connected }

    public init(id: String) { self.id = id }
    public func connect() { state = .connecting; retryCount += 1 }
}

extension BluetoothSession {
    fileprivate func logAttempt() { debugLog.append("attempt \(retryCount)") }   // truy cập được private ở extension cùng file
}

open class PluginBase {                            // framework cho phép bên ngoài kế thừa
    public init() {}
    open func hook() {}
}

    4. Kế thừa (inheritance): override, super, final và khởi tạo¶

    Kế thừa cho phép lớp con dùng lại và mở rộng lớp cha. Swift chỉ có đơn kế thừa (một lớp cha). Từ khóa: • override: bắt buộc khi ghi đè method/property của cha (tránh ghi đè nhầm). • super: gọi bản của lớp cha. • final: cấm kế thừa lớp hoặc override một thành viên; vừa tài liệu hóa ý định vừa cho compiler tối ưu (static dispatch). • class func/class var: thành viên cấp kiểu mà subclass override được (static thì không).

    Quy tắc khởi tạo (Swift book): (1) designated init phải gọi designated init của lớp cha; (2) convenience init phải gọi một init khác của cùng lớp; (3) convenience init cuối cùng phải dẫn tới một designated init. Hai pha: pha 1 gán mọi thuộc tính (subclass trước, rồi super.init), pha 2 mới được dùng self.

    Không có abstract class. Cách thay thế: dùng protocol, hoặc mẫu "template method" với lớp cha cung cấp bộ khung và method cần override gọi fatalError (chỉ phát hiện lỗi lúc chạy, nên protocol thường tốt hơn).

    class Vehicle {
    let id: String
    init(id: String) { self.id = id }

    func startDiagnostics() -> String { "Generic scan for \(id)" }
    final func label() -> String { "[\(id)]" }          // không cho override
    class func category() -> String { "vehicle" }       // subclass override được
}

final class ElectricCar: Vehicle {
    var batteryPercent = 100

    override func startDiagnostics() -> String {
        super.startDiagnostics() + " + battery \(batteryPercent)%"
    }
    override class func category() -> String { "ev" }
}

print(ElectricCar(id: "B").startDiagnostics())
print(Vehicle.category(), ElectricCar.category())      // vehicle ev

// Template method thay cho abstract class
class ReportGenerator {
    func generate() -> String { header() + body() }
    func header() -> String { "REPORT\n" }
    func body() -> String { fatalError("Subclass must override body()") }
}
final class CsvReport: ReportGenerator {
    override func body() -> String { "a,b,c" }
}
print(CsvReport().generate())

    5. Đa hình (polymorphism): ba dạng trong Swift¶

    Đa hình là cùng một lời gọi nhưng hành vi tùy kiểu thật. Swift có ba dạng, mỗi dạng có chi phí và độ linh hoạt khác nhau: 1. Subtype polymorphism (kế thừa): [Vehicle] chứa ElectricCar; method được chọn lúc chạy (vtable). Linh hoạt nhất nhưng gắn chặt vào cây kế thừa và chỉ cho class. 2. Protocol polymorphism: [any Scannable] chứa mọi kiểu conform, kể cả struct/enum; dispatch qua protocol witness table. Không cần lớp cha chung. 3. Parametric polymorphism (generics): func runAll<S: Scannable>(_:) được chuyên biệt hóa lúc biên dịch, nhanh nhất, nhưng kiểu phải xác định tại điểm gọi.

    Chọn: cần một tập kiểu khác nhau lẫn trong một collection → protocol (any); tất cả cùng một kiểu cụ thể nhưng muốn tái sử dụng thuật toán → generics; có sẵn cây class (UIKit) hoặc cần chia sẻ trạng thái → kế thừa.

    class Vehicle {
    let name: String
    init(name: String) { self.name = name }
    func describe() -> String { "Vehicle \(name)" }
}
final class ElectricCar: Vehicle {
    override func describe() -> String { "EV \(name)" }
}

// 1. Kế thừa
let fleet: [Vehicle] = [Vehicle(name: "A"), ElectricCar(name: "B")]
for v in fleet { print(v.describe()) }

// 2. Protocol
protocol Scannable { func scan() -> String }
struct ObdScanner: Scannable { func scan() -> String { "OBD scan" } }
struct BleScanner: Scannable { func scan() -> String { "BLE scan" } }
let scanners: [any Scannable] = [ObdScanner(), BleScanner()]
for s in scanners { print(s.scan()) }

// 3. Generics
func runAll<S: Scannable>(_ scanners: [S]) -> [String] { scanners.map { $0.scan() } }
print(runAll([ObdScanner(), ObdScanner()]))

    6. Trừu tượng (abstraction): protocol thay cho abstract class¶

    Trừu tượng hóa là tách "làm gì" khỏi "làm thế nào". Trong Swift công cụ chính là protocol: • Protocol khai báo hợp đồng (property, method, initializer). • Protocol extension cung cấp cài đặt mặc định dùng chung, thay cho phần code chung ở lớp cha abstract. • associatedtype cho phép hợp đồng generic. • Một kiểu conform nhiều protocol (thay cho đa kế thừa). • Struct/enum cũng conform được nên giữ value semantics.

    So với abstract class: không cần cây kế thừa, không có vấn đề "lớp cha mong manh" (sửa lớp cha làm vỡ lớp con), không bị buộc dùng reference type, dễ mock khi test. Điểm yếu: không chia sẻ được stored property mặc định (phải đặt ở từng kiểu), và dispatch của hàm chỉ có trong extension (không khai báo trong protocol) là tĩnh.

    protocol Exportable {
    var fileName: String { get }
    func render() -> String
}

extension Exportable {
    func export() -> String { "== \(fileName) ==\n" + render() }     // cài đặt dùng chung
}

struct CsvReport: Exportable {
    let fileName = "report.csv"
    func render() -> String { "a,b,c" }
}
struct JsonReport: Exportable {
    let fileName = "report.json"
    func render() -> String { "{ }" }
}

func save(_ item: some Exportable) { print(item.export()) }    // phụ thuộc hợp đồng, không phụ thuộc kiểu cụ thể
save(CsvReport())
save(JsonReport())

    7. Composition over inheritance: ví dụ thiết kế Vehicle Diagnostics¶

    "Ưu tiên composition hơn kế thừa" nghĩa là xây hành vi bằng cách ghép các thành phần nhỏ thay vì đặt mọi thứ trong một cây phân cấp. Cây kế thừa phát sinh vấn đề khi yêu cầu thay đổi: • Vehicle → ElectricCar, rồi có HybridCar (vừa điện vừa xăng) thì kế thừa từ ai? • Thêm Truck, ElectricTruck, HybridTruck: số lớp nổ tung. • Lớp con dính chặt vào chi tiết lớp cha.

    Giải pháp: mô tả khả năng bằng protocol nhỏ và đặc điểm bằng enum/struct; ghép chúng lại. Ví dụ dưới đây dùng Powertrain (enum) thay cho cây ElectricCar/HybridCar; dùng protocol composition (Chargeable & Refuelable) cho những hàm cần cả hai khả năng.

    protocol Chargeable { var batteryPercent: Int { get } }
protocol Refuelable { var fuelLiters: Double { get } }

enum Powertrain {
    case gasoline(fuelLiters: Double)
    case electric(batteryPercent: Int)
    case hybrid(fuelLiters: Double, batteryPercent: Int)
}

struct Vehicle {
    let id: String
    var powertrain: Powertrain

    var rangeKm: Double {
        switch powertrain {
        case .gasoline(let liters):           return liters * 12
        case .electric(let percent):          return Double(percent) * 4
        case .hybrid(let liters, let percent): return liters * 12 + Double(percent) * 4
        }
    }
}

struct HybridState: Chargeable, Refuelable {
    let batteryPercent: Int
    let fuelLiters: Double
}

func plan(_ state: some Chargeable & Refuelable) -> String {
    "Pin \(state.batteryPercent)%, xăng \(state.fuelLiters)L"
}

print(Vehicle(id: "V1", powertrain: .hybrid(fuelLiters: 20, batteryPercent: 50)).rangeKm)   // 440.0
print(plan(HybridState(batteryPercent: 50, fuelLiters: 20)))

    8. OOP, Functional và Protocol-oriented: chọn thế nào¶

    Ba mô hình không loại trừ nhau; code Swift tốt thường pha trộn: • Value-oriented + functional: dữ liệu là struct/enum bất biến, biến đổi bằng map/filter/reduce, hàm thuần. Dùng cho model, tính toán, validation, định dạng. • Protocol-oriented: hợp đồng ở ranh giới (repository, service, client), cho phép thay implementation và mock. • Object-oriented (class): khi cần identity chung, vòng đời có deinit, trạng thái mutable được chia sẻ (BLE session, cache), hoặc tích hợp UIKit/Objective-C. Nếu truy cập đồng thời từ nhiều luồng thì xem xét actor (tuần 7).

    Bảng quyết định nhanh: • Dữ liệu thuần, có thể sao chép → struct. • Một tập hữu hạn trạng thái/kết quả → enum. • Khả năng cần thay thế/mock → protocol. • Có identity, vòng đời hoặc chia sẻ trạng thái → final class (hoặc actor). • Cần kế thừa thật sự (framework UIKit) → class có kế thừa. • Biến đổi dữ liệu → hàm thuần + map/filter/reduce.

    9. SOLID trong Swift¶

    • S (Single Responsibility): mỗi kiểu chỉ có một lý do thay đổi; tách ViewModel, repository, validator (tuần 7). • O (Open/Closed): mở cho mở rộng, đóng cho sửa đổi; thêm kiểu mới conform protocol thay vì sửa switch/if trung tâm. • L (Liskov Substitution): subtype dùng thay supertype không phá hợp đồng. Ví dụ vi phạm điển hình ở dưới. • I (Interface Segregation): protocol nhỏ theo vai trò thay vì "god protocol". • D (Dependency Inversion): phụ thuộc vào protocol, truyền dependency qua initializer (tuần 2, 7).

    // Vi phạm Liskov: subclass phá vỡ hợp đồng của lớp cha
class Bird { func fly() { print("flying") } }
final class Penguin: Bird {
    override func fly() { fatalError("Penguin can't fly") }     // người gọi Bird.fly() bị crash bất ngờ
}

// Sửa: tách khả năng thành protocol, kiểu nào có khả năng thì conform
protocol Flyer { func fly() }
struct Sparrow: Flyer { func fly() { print("flying") } }
struct PenguinBird { func swim() { print("swimming") } }       // không là Flyer

func release(_ flyer: some Flyer) { flyer.fly() }              // chỉ nhận kiểu thật sự bay được
release(Sparrow())

    10. So sánh với TypeScript, Java và Kotlin¶

    • class TS ~ class Swift, nhưng TS là reference và có prototype động, Swift có struct (value) và enum mạnh. • private/protected/public TS ~ private/fileprivate/internal/public/open Swift; không có protected. • abstract class TS/Java ~ protocol (+ protocol extension) của Swift. • interface TS ~ protocol, nhưng Swift bắt buộc khai báo conform tường minh (không structural typing). • extends ~ : SuperClass; implements ~ : Protocol; đa kế thừa không có (chỉ đơn kế thừa class, nhiều protocol). • final Java ~ final; @Override ~ override (bắt buộc). • Kotlin data class ~ struct (+ Equatable/Hashable/Codable); Kotlin extension function ~ extension. • Generics TS bị xóa sau khi biên dịch; generics Swift được giữ và chuyên biệt hóa. • Quản lý bộ nhớ: JS/Java/Kotlin dùng GC; Swift dùng ARC nên cần chú ý retain cycle. • Angular service singleton (providedIn: 'root') ~ class dùng chung truyền qua initializer hoặc @Environment.

    11. Lỗi thường gặp¶

    1. Dùng class và kế thừa cho mọi model: dễ gặp shared mutable state và cây phân cấp cứng nhắc; ưu tiên struct + protocol.
    2. Cây kế thừa quá sâu hoặc kế thừa chỉ để "dùng lại code": dùng composition hoặc protocol extension.
    3. Quên final cho class không dự định kế thừa.
    4. Viết init sai thứ tự hai pha: gọi super.init trước khi gán thuộc tính của subclass.
    5. Mở public/open không cần thiết, rò rỉ chi tiết nội bộ.
    6. Đặt method trong protocol extension mà không khai báo trong protocol rồi ngạc nhiên vì không được "override".
    7. Dùng nhiều is/as? thay vì đa hình.
    8. Vi phạm Liskov: subclass ném lỗi/fatalError ở method của cha.
    9. Retain cycle giữa hai class tham chiếu nhau mạnh (tuần 3).
    10. Lạm dụng singleton shared: khó test, ẩn phụ thuộc.

    12. Tóm tắt¶

    • Swift là đa mô hình, thiên về "value types first, protocols over inheritance". • Đóng gói: access control + private(set); không có protected. • Kế thừa: đơn kế thừa, override/super/final, khởi tạo hai pha; không có abstract class. • Đa hình: kế thừa, protocol, generics; chọn theo nhu cầu và chi phí. • Trừu tượng: protocol + protocol extension + associatedtype. • Composition over inheritance; kết hợp functional cho biến đổi dữ liệu. • Dùng class khi có identity/vòng đời/UIKit; còn lại ưu tiên struct, enum, protocol.

    Bài tập¶

    Tự làm trước, rồi mới mở gợi ý / đáp án.

    Thực hành 1 — Thay cây kế thừa bằng composition¶

    Cho cây Vehicle → ElectricCar → HybridCar, trong đó HybridCar phải copy code xăng từ một lớp khác. Thiết kế lại bằng enum Powertrain và hàm rangeKm trên struct Vehicle. Thêm loại "hydrogen" mà không tạo lớp mới.

    Gợi ý Thêm một case vào Powertrain và một nhánh trong switch.
    Đáp án 
    enum Powertrain {
    case gasoline(fuelLiters: Double)
    case electric(batteryPercent: Int)
    case hybrid(fuelLiters: Double, batteryPercent: Int)
    case hydrogen(kilograms: Double)                  // loại mới: chỉ thêm một case
}

struct Vehicle {
    let id: String
    var powertrain: Powertrain
    var rangeKm: Double {
        switch powertrain {
        case .gasoline(let l):               return l * 12
        case .electric(let p):               return Double(p) * 4
        case .hybrid(let l, let p):          return l * 12 + Double(p) * 4
        case .hydrogen(let kg):              return kg * 100
        }
    }
}
print(Vehicle(id: "H1", powertrain: .hydrogen(kilograms: 5)).rangeKm)   // 500.0
    **Giải thích:** Switch exhaustive buộc bạn xử lý case mới ở mọi nơi dùng `powertrain`, compiler chỉ ra chỗ còn thiếu. Không có lớp con nào phải sửa, và không lặp code giữa các lớp.

    Thực hành 2 — Sửa vi phạm Liskov¶

    Cho class Report { func export() -> String } và final class ReadOnlyReport: Report override export() bằng fatalError("không được phép"). Giải thích vì sao vi phạm Liskov và thiết kế lại bằng protocol nhỏ.

    Gợi ý Tách khả năng "xuất" (Exportable) khỏi khả năng "chỉ xem" (Viewable).
    Đáp án 
    protocol Viewable { func view() -> String }
protocol Exportable { func export() -> String }

struct EditableReport: Viewable, Exportable {
    func view() -> String { "content" }
    func export() -> String { "file.csv" }
}

struct ReadOnlyReport: Viewable {                  // không là Exportable: không thể bị gọi export() nhầm
    func view() -> String { "content" }
}

func share(_ item: some Exportable) { print(item.export()) }   // compiler chỉ nhận kiểu export được
share(EditableReport())
    **Giải thích:** Với kế thừa, người gọi `Report.export()` tin hợp đồng luôn thành công; subclass `fatalError` phá vỡ nó. Tách protocol khiến lỗi bị bắt lúc biên dịch thay vì crash lúc chạy.

    Thực hành 3 — Audit access control¶

    Cho lớp TokenManager có var token: String?, var refreshTimer: Timer?, func refresh() và func saveToKeychain(). Chỉ ra mức truy cập hợp lý cho từng thành viên nếu bên ngoài chỉ cần đọc token và gọi refresh().

    Gợi ý private(set) cho token; private cho phần còn lại.
    Đáp án 
    import Foundation

final class TokenManager {
    private(set) var token: String?          // đọc ở ngoài, chỉ lớp được ghi
    private var refreshTimer: Timer?         // chi tiết nội bộ

    func refresh() {                         // giao diện công khai (internal)
        token = "new-token"
        saveToKeychain()
        scheduleRefresh()
    }

    private func saveToKeychain() { }        // nội bộ
    private func scheduleRefresh() {
        refreshTimer?.invalidate()
        refreshTimer = Timer.scheduledTimer(withTimeInterval: 3000, repeats: false) { [weak self] _ in
            self?.refresh()
        }
    }
}
    **Giải thích:** Giao diện công khai nhỏ nhất có thể giúp bảo vệ bất biến (không ai gán token tùy ý) và cho phép đổi cách cài đặt (Keychain, timer) mà không ảnh hưởng người dùng lớp.

    Thực hành 4 — Chọn công cụ¶

    Chọn giữa struct, enum, protocol, final class hay actor cho: (a) Vehicle dữ liệu xe; (b) trạng thái kết nối BLE; (c) hợp đồng VehicleRepository; (d) phiên kết nối BLE dùng chung cho nhiều màn hình; (e) bộ nhớ đệm được nhiều task truy cập đồng thời.

    Gợi ý Hỏi: dữ liệu thuần? tập trạng thái hữu hạn? cần thay thế? có identity? truy cập đồng thời?
    Đáp án 
    (a) struct          — dữ liệu thuần, sao chép được, Equatable/Codable.
(b) enum            — tập trạng thái hữu hạn (idle, connecting, connected, failed).
(c) protocol        — hợp đồng để thay thế/mock (in-memory, REST, SwiftData).
(d) final class     — có identity và vòng đời (deinit), chia sẻ trạng thái; @MainActor nếu gắn với UI.
(e) actor           — trạng thái mutable chia sẻ, truy cập đồng thời an toàn.
    **Giải thích:** Quy tắc: ưu tiên kiểu giá trị và protocol; class cho identity/vòng đời; actor cho trạng thái mutable dùng chung giữa nhiều luồng.
