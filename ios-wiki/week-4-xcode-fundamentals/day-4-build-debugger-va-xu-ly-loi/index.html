    Tuần 4 · Ngày 4 · Build, debugger và xử lý lỗi¶

    Mục tiêu: Phân loại lỗi, đọc thông báo của compiler và dùng breakpoint, call stack, LLDB để tìm nguyên nhân.
    Thời lượng: 75–90 phút

    Khái niệm: compile-time errors, runtime errors, logic bugs, breakpoints, call stack, LLDB, os.Logger

    • Đã đọc xong
    • Đã làm hết bài tập

    1. Ba loại lỗi và cách tiếp cận¶

    1. Lỗi compile-time: code không biên dịch được. Xcode đánh dấu đỏ, liệt kê ở Issue navigator. Ví dụ: sai kiểu, thiếu try, switch không exhaustive. Đọc thông báo, các gợi ý Fix-it thường chỉ đúng chỗ.
    2. Lỗi runtime: app chạy rồi crash hoặc ném lỗi. Ví dụ: force unwrap nil, index out of range, chia cho 0, dùng sai thread. Console in lỗi và dừng ở dòng gây crash.
    3. Lỗi logic: app chạy không crash nhưng kết quả sai (lọc sai, tính sai, state không cập nhật). Đây là loại khó nhất vì không có thông báo; bạn phải quan sát luồng dữ liệu bằng debugger hoặc log.

    Phương pháp: tái hiện ổn định → khoanh vùng (log hoặc breakpoint) → đưa ra giả thuyết → kiểm chứng → sửa → viết test để không tái phát.

    2. Đọc lỗi compile của Swift¶

    Lỗi Swift đôi khi dài và gây nhầm. Mẹo đọc: • Bắt đầu từ lỗi đầu tiên (trên cùng): các lỗi sau có thể là hệ quả. • Đọc đúng chữ: "Cannot convert value of type 'Int' to expected argument type 'Double'" nghĩa là chuyển kiểu rõ ràng. • "Value of optional type 'String?' must be unwrapped": cần if let/guard let/??. • "Type 'X' does not conform to protocol 'Y'": thiếu requirement; bấm Fix để sinh stub. • "Missing return in a function expected to return": có nhánh không trả giá trị. • "Cannot find 'x' in scope": sai tên, quên import, hoặc file không thuộc target. • Lỗi SwiftUI kiểu "The compiler is unable to type-check this expression in reasonable time": biểu thức quá phức tạp, hãy tách view/biến cục bộ.

    Thử ⇧⌘K và build lại nếu thấy lỗi vô lý, hoặc nếu sau khi đổi branch.

    3. Breakpoint và bước chạy¶

    Click vào lề trái của dòng code để đặt breakpoint (hình mũi tên xanh). Khi chạy tới đó, app dừng; Debug area hiển thị biến cục bộ (Variables View) và console LLDB.

    Điều khiển: • Continue (⌃⌘Y): chạy tiếp tới breakpoint kế. • Step Over (F6): chạy dòng hiện tại, không vào hàm. • Step Into (F7): vào bên trong hàm được gọi. • Step Out (F8): chạy hết hàm hiện tại, quay về nơi gọi.

    Breakpoint nâng cao: Conditional (chỉ dừng khi biểu thức đúng, ví dụ vehicle.year < 2000), Action (in log hoặc chạy lệnh rồi tự tiếp tục, không dừng), Exception Breakpoint (dừng ngay lúc có lỗi/ném exception; thêm trong Breakpoint navigator ⌘8), Symbolic Breakpoint.

    4. Call stack và LLDB¶

    Debug navigator (⌘7) hiển thị call stack: chuỗi hàm đã gọi để tới điểm hiện tại, mới nhất ở trên. Khi crash, nhìn dòng đầu tiên thuộc code của bạn trong stack để biết điểm phát sinh, và các khung bên dưới cho biết nó được gọi từ đâu.

    Trong console LLDB (khi đang dừng) dùng: • po expression: in giá trị (print object), ví dụ po vehicles.count, po vehicle. • p expression: in kèm kiểu. • expr var = value: sửa biến lúc đang chạy để thử giả thuyết. • bt: in backtrace. • frame variable: liệt kê biến trong khung hiện tại.

    Với lỗi kiểu "Fatal error: Unexpectedly found nil while unwrapping an Optional value", dòng chỉ ra file và số dòng chính xác; từ đó hỏi: vì sao giá trị này nil? Ai đã gán, khi nào?

    5. Logging đúng cách¶

    print tiện nhưng hạn chế. Với app thật, dùng os.Logger (framework os): có mức độ (debug, info, error), phân loại theo subsystem/category, hiển thị trong Console.app, tắt được trong Release, và không lộ dữ liệu nhạy cảm theo mặc định (giá trị động bị che trừ khi privacy: .public).

    Nguyên tắc: log sự kiện (kết nối BLE bắt đầu/kết thúc, request URL không kèm token, lỗi) chứ không log dữ liệu cá nhân hay secret. Đừng để log gây chậm trong vòng lặp nóng.

    import os

private let logger = Logger(subsystem: "com.yourcompany.VehicleDiagnostics", category: "bluetooth")

func connect(deviceID: String) {
    logger.info("Bắt đầu kết nối \(deviceID, privacy: .public)")
    // ...
    logger.error("Kết nối thất bại, thử lại")
    logger.debug("Chi tiết nội bộ chỉ có khi debug")
}

    6. So sánh với DevTools của trình duyệt và lỗi thường gặp¶

    So sánh: • debugger; và breakpoint trong Chrome ~ breakpoint Xcode. • console.log ~ print/Logger; tab Network ~ Instruments Network hoặc Proxyman/Charles. • Watch expressions ~ Variables View và po. • Lỗi build (Webpack) ~ Issue navigator.

    Lỗi thường gặp: 1. Sửa lung tung khi chưa tái hiện được lỗi. 2. Chỉ đọc dòng cuối của thông báo lỗi dài. 3. Quên bật Exception Breakpoint nên không biết crash ở đâu. 4. Dùng print để debug rồi quên xóa/để lộ dữ liệu nhạy cảm. 5. Không đọc call stack: chỉ nhìn dòng crash, bỏ lỡ nguyên nhân thật xảy ra trước đó. 6. Sửa triệu chứng bằng ! hoặc ??... thay vì tìm nguyên nhân. 7. Debug trên Release mà thấy biến bị "optimized out": hãy debug bằng Debug configuration.

    7. Tóm tắt¶

    • Ba loại lỗi: compile-time, runtime, logic; mỗi loại có cách tiếp cận khác nhau. • Đọc lỗi từ trên xuống, bắt đầu từ lỗi đầu tiên. • Breakpoint, Step Over/Into/Out, conditional và exception breakpoint là công cụ chính. • Call stack cho biết đường đi tới lỗi; LLDB (po, bt, expr) để kiểm tra khi dừng. • Dùng os.Logger cho log có cấu trúc, tránh log dữ liệu nhạy cảm.

    Bài tập¶

    Tự làm trước, rồi mới mở gợi ý / đáp án.

    Bài 1 — Phân loại lỗi¶

    Phân loại: (a) let n: Int = "5"; (b) let arr = [1,2,3]; print(arr[5]); (c) hàm lọc xe "từ 2020" nhưng dùng year > 2020 nên bỏ sót xe 2020.

    Gợi ý Lỗi nào do compiler bắt, lỗi nào làm crash, lỗi nào chạy bình thường nhưng sai?
    Đáp án (a) Compile-time: không gán String cho Int. (b) Runtime: "Fatal error: Index out of range" khi chạy. (c) Logic: chạy bình thường nhưng kết quả sai (cần dùng >= 2020). **Giải thích:** Loại lỗi quyết định công cụ: compile-time đọc Issue navigator, runtime đọc call stack, logic cần breakpoint/log và test.

    Bài 2 — Tìm lỗi bằng breakpoint¶

    Cho func recentCount(_ years: [Int]) -> Int { years.filter { $0 > 2020 }.count } được kỳ vọng đếm năm từ 2020. Đặt breakpoint, dùng po để kiểm tra và tìm lỗi logic.

    Gợi ý Đặt breakpoint trong closure hoặc chia nhỏ biểu thức ra biến để quan sát.
    Đáp án 
    func recentCount(_ years: [Int]) -> Int {
    let recent = years.filter { $0 >= 2020 }   // sửa: > thành >=
    return recent.count                         // đặt breakpoint ở dòng này
}

// Trong LLDB:
// (lldb) po years
// (lldb) po recent
// So sánh thấy 2020 bị loại khi dùng '>'.
    **Giải thích:** Tách biểu thức thành biến trung gian giúp breakpoint quan sát được từng bước. `po recent` cho thấy 2020 vắng mặt, dẫn tới việc sửa toán tử.

    Bài 3 — Đọc crash¶

    App crash với "Fatal error: Unexpectedly found nil while unwrapping an Optional value" ở let name = vehicle.owner!.name. Nêu các bước điều tra và cách sửa an toàn.

    Gợi ý Xem call stack để biết ai truyền vehicle; hỏi vì sao owner nil; sửa bằng xử lý Optional hoặc đảm bảo dữ liệu.
    Đáp án 
    Các bước:
1. Đọc dòng crash: file, dòng, giá trị nào nil (vehicle.owner).
2. Xem call stack để biết hàm nào gọi, dữ liệu vehicle từ đâu.
3. Dùng po vehicle để xem owner thực sự là nil; truy ngược nơi gán.
4. Quyết định: owner có được phép vắng không? Nếu có thì xử lý, nếu không thì sửa nguồn dữ liệu.

Sửa an toàn:
let name = vehicle.owner?.name ?? "Chưa có chủ xe"
    **Giải thích:** Không chỉ vá bằng `??`; cần biết nil là hợp lệ hay là dấu hiệu dữ liệu sai. Thêm test cho trường hợp `owner == nil` để không tái phát.

    Bài 4 — Log có cấu trúc¶

    Thay print("connected \(id)") bằng os.Logger với subsystem, category và mức phù hợp. Vì sao nên dùng Logger thay vì print trong app thật?

    Gợi ý Logger(subsystem:category:) và logger.info.
    Đáp án 
    import os

private let logger = Logger(subsystem: "com.yourcompany.VehicleDiagnostics", category: "bluetooth")

func didConnect(id: String) {
    logger.info("Connected to \(id, privacy: .public)")
}
    **Giải thích:** Logger có mức độ, phân loại, hiển thị trong Console.app, tắt/giảm được ở Release và che dữ liệu động mặc định, phù hợp cho chẩn đoán trên thiết bị người dùng.
