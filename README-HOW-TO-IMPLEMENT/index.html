    5.2 Bytes → value (BluetoothDecoder.decode)¶

    UUID Example bytes Result Rule
    2A19 Battery Level 5A 90 % uint8
    2A00 2A24–2A29 (device name, model, serial, firmware, hardware, software, manufacturer) 4E 6F 72 64 69 63 Nordic UTF-8, trailing 00 byte dropped
    2A37 Heart Rate 00 48 · 01 2C 01 72 bpm · 300 bpm bit 0 of the flags byte: 0 → uint8, 1 → uint16 LE
    2A01 Appearance 41 09 0x0941 uint16 LE
    unknown, all printable 41 54 0D "AT\r" treated as ASCII text (UART dongles answer in text)
    unknown, 1 / 2 / 4 bytes 34 12 4660 (uint16 LE) little-endian number
    unknown, anything else 01 02 03 — hex only

    6. Day 4 — Notify + disconnect + errors¶

    Schedule: Thu 24/09 — Steps 7–9 + full-flow test. Do: subscribe to 1 notify characteristic, route data → event → UI, handle manual + unexpected disconnect, clean up subscriptions. Target: the whole scan → … → disconnect flow works; the UI reflects every state including errors.

    6.0 How notify works (read before 6.1)¶

    The idea in one sentence: Read = the app asks and the peripheral answers once (pull). Notify = the app subscribes once, and from then on the peripheral pushes by itself whenever the value changes (push) — like subscribing to SMS alerts instead of phoning every second to ask. No "ask" packets, no polling lag, and the peripheral can sleep when there's nothing new.

    All 3 pieces are needed — miss any one and it's silent, no error:

    # Piece Where it lives Who handles it
    1 The characteristic has the NOTIFY or INDICATE property peripheral (declared in its GATT) readable after discovery → the Notify button only shows when present (GattSection)
    2 Descriptor CCCD 2902 = the "switch" on the peripheral: 01 00 notify · 02 00 indicate · 00 00 off peripheral the app writes it → only then does the peripheral start pushing
    3 The phone's OS agrees to route packets to the app phone 🤖 setCharacteristicNotification(c, true) · 🍎 CoreBluetooth does it itself

    What goes over the air (ATT — the layer below GATT):

     App (UI → Service)           OS Bluetooth stack                 Peripheral (dongle / ESP32 / nRF)
 ──────────────────           ──────────────────                 ─────────────────────────────────
 [Notify] tapped
   │ 🤖 setCharacteristicNotification(c,true) ─► (piece 3: "packets for c go to this app")
   │ 🤖 writeDescriptor(2902, 01 00)  ┐
   │ 🍎 setNotifyValue(true, ch) ─────┴──────► ATT Write Request  (CCCD handle = 01 00) ──►  CCCD := notify
   │                                         ◄── ATT Write Response (ok / error) ◄──────────┘
   │ 🤖 onDescriptorWrite(status) · 🍎 didUpdateNotificationStateFor(error)
   ▼ isNotifying = true → [Stop] button
                                                                  value changes (counter ticks, OBD answers…)
                                         ◄── ATT Handle Value Notification (handle, bytes) ── repeats forever
   🤖 onCharacteristicChanged(c, bytes) ◄──┘   (NO acknowledgement goes back)
   🍎 didUpdateValueFor(ch)            ◄──┘
   └─► GattValue(NOTIFY) ─► received (≤ 50) ─► ReceivedDataSection draws a new line

 [Stop] = exactly the same but writes CCCD 00 00 (🤖 write + setCharacteristicNotification(false) · 🍎 setNotifyValue(false))

    Notify vs Indicate — the code picks automatically from the property (BluetoothClientService.kt:585; 🍎 CoreBluetooth picks itself):

    Notify (01 00) Indicate (02 00)
    Acknowledgement none — fire and forget every packet needs a Confirmation from the phone (the OS sends it, the app does nothing)
    Speed fast, several packets per connection interval slow: the next packet waits for the previous confirmation
    Packet loss possible (weak signal, app too slow) no loss (the link layer retransmits)
    Typical use sensor streams, ESP32 counters, the dongle's UART FFE1 important events (Service Changed 2A05, commands that must arrive)

    The subscription lifetime — tied to one connection, not to the app:

    • Disconnect (manual / signal lost / radio off) → the subscription is gone. An unbonded peripheral resets CCCD to 00 00; the next connection must discover again and tap Notify again (auto-resubscribe not done yet — §8.5 item 1).
    • A bonded peripheral remembers CCCD across connections → you should write 00 00 before disconnecting; the current version only turns it off on the OS side (BluetoothClientService.kt:485).
    • BluetoothGattCharacteristic / CBCharacteristic handles die with the connection → that's why every disconnect path calls clearGattState() (§6.3).
    • 🍎 The app goes to the background without UIBackgroundModes = bluetooth-central → iOS stops delivering packets; 🤖 keeps going until the process is killed (foreground service is Week 3).

    The path of one packet through the code (data → event → UI):

    Step 🤖 Android 🍎 iOS
    Packet arrives (BLE stack thread) :423 onCharacteristicChanged(g, c, value) (API 33+) · :429 the old variant must c.value.copyOf() immediately :648 didUpdateValueFor
    Tell read from notify 2 different callbacks → not needed shared callback with read → :498 handleValue: key in pendingReads = READ, otherwise NOTIFY
    Back to the main thread scope.launch { } (scope = Main) @MainActor class
    Bytes → value valueOf(c, bytes, NOTIFY) → BluetoothDecoder.decode (§5.2) same as 🤖
    Store (keep the latest 50 lines) :608 handleNotified → appendCapped → _received: StateFlow :518 received = appendCapped(…) (@Observable)
    Draw collectAsState() → ReceivedDataSection ReceivedDataSection redraws by itself

    Limits to know:

    • Default MTU is 23 → each notify packet carries at most 20 bytes of data; anything longer the peripheral sends is truncated. Task 004: 🤖 requestMtu(247) after discovery, 🍎 iOS negotiates itself; the GATT block shows MTU … · max … bytes per packet (§8.4).
    • Throughput is capped by the connection interval (usually 15–50 ms) × packets per interval; if the ESP32 pushes faster than that, notify packets are dropped and nobody reports it.
    • CarMD dongle: FFE1 is a UART port — enabling notify succeeds but no packets arrive until the app writes a command (ATZ\r, 010C\r…) into it; only then does the dongle's answer come back via notify. So for the dongle: Notify = the ears, Write = the mouth — Day 4 has the ears, task 004 adds the mouth (§8.4).

    Tapped Notify but no lines appear — check in this order:

    1. Did the button turn into Stop? No → subscribe failed, read the red text (has no CCCD / status=…) — piece 2 is missing.
    2. It's Stop but still empty → is the peripheral really changing the value? (The nRF server must press send; the dongle must receive a written command first.)
    3. Logs: 🤖 adb logcat -s BleClient look for NOTIFY · 🍎 console [BleClient]. Log present but UI empty → a UI-layer bug; no log → packets never reach the app.
    4. Just reconnected? → the old subscription is gone, tap Notify again.

    Point Reason
    The app must be in the foreground iOS drops the Local Name when the app goes to the background, and the Service UUID moves into an "overflow" area only other iPhones can read → Android sees nothing

    Don't filter by MAC iPhones use a random address that rotates periodically → the MAC differs every test
    The name may not be CMD-Test 🤖 the code reads device.name first, then scanRecord.deviceName (BluetoothClientService.kt:223). If Android was ever paired with that iPhone it shows the system name ("…'s iPhone"); the first packet without a scan response shows Unknown. Look for the strongest RSSI

    Phone A (Android) needs:

    • Bluetooth on. Android 12+ (API 31+): grant the Nearby devices permission. Android ≤ 11: also turn on Location (the system switch) + grant location permission, otherwise scanning returns 0 results with no error.
    • Scanner tab: CarMD tools only off (unless the name has CMD-), the Device Name box empty.
    • Keep the 2 phones close together.

    Can't see it? Narrow it down in this order:

    1. Install nRF Connect on Android A → Scanner, no filters → does it see iPhone B? No = the problem is on iPhone B or phone A's permissions/Location, not the app.

    Things to remember - Pick the write type from the properties. Has WRITE → with response (the peripheral ACKs, real errors come back). Only WRITE NO RESP → without response. 🍎 with the wrong type CoreBluetooth drops the write and only prints a warning; 🤖 usually returns an error status. - Without response doesn't mean the peripheral received it. 🤖 onCharacteristicWrite still arrives but only means "pushed down the stack"; 🍎 there's no callback at all. To be sure → use with response, or wait for the answer via notify (dongle). - The write callback doesn't return the bytes. You must keep them yourself (pendingWrite 🤖 / pendingWrites[key] 🍎) to print the WRITE line in Received Data. - 🤖 MTU is a GATT op → goes through gattOps. Calling requestMtu while another op is running = returns false, op lost. onMtuChanged can also arrive when the peripheral requests it → only opDone() when the in-flight op really is Request MTU. - 🍎 you can't request an MTU. iOS negotiates on connect (usually 185 or more); the app only reads maximumWriteValueLength(for: .withoutResponse) = MTU − 3. Don't read the .withResponse variant — it returns 512 because iOS splits "long writes" itself. - Longer than MTU − 3 is blocked, no automatic splitting (see Out of scope in task 004). ELM327 commands are only a few bytes so it's enough. - ELM327 dongles need \r at the end of a command. Without 0x0D the dongle waits and never answers — that's why Text mode accepts the \r escape, and every preset includes \r.

    9. Note: BLE object model (Day 1 exercise)¶

      CENTRAL (this app: the phone)                 PERIPHERAL (dongle / ESP32 / nRF Advertiser)
  ─────────────────────────────                 ─────────────────────────────────────────────
  scan  ◄──────── advertising packet ────────── advertises: name, service UUID, manufacturer data
  connect ─────────────────────────────────────► GATT server
                                                 └─ Service  (UUID, e.g. 180F Battery / FFE0 dongle)
                                                     └─ Characteristic (UUID + properties)
                                                          ├─ value (bytes)
                                                          └─ Descriptor 2902 (CCCD: notify on/off)
  read   ──── ask once ───────────────────────►  value            (the central pulls)
  write  ──── send bytes ─────────────────────►  value            (with / without response)
  notify ◄─── peripheral pushes on change ─────  value            (CCCD must be enabled first)
    • Central / peripheral: a role during the connection, not a kind of device. The central scans + connects; the peripheral advertises + waits.
    • Service: a group of functionality (Battery, Heart Rate, the dongle's UART port). Characteristic: one data slot inside a service, whose properties say READ / WRITE / NOTIFY.
    • UUID: the name of a service/characteristic. 16-bit (180F) is a SIG standard = 0000180F-0000-1000-8000-00805F9B34FB; 128-bit is self-assigned.
    • Read = pull once · Write = push down · Notify = the peripheral pushes up continuously, cheaper than polling.

    10. Explained for beginners¶

    PermissionStatus with 4 states (instead of Boolean granted) - What: tells apart never asked / granted / denied but can ask again / only Settings left. - Why: each state needs a different button. Collapse them into false → "Request" shows when the dialog is dead, the user taps, nothing happens, they think the app is broken. - Ref: Android — Request runtime permissions

    The "asked" flag in SharedPreferences (Android only) - What: remembers which permissions the app has ever shown a dialog for. - Why: checkSelfPermission + shouldShowRequestPermissionRationale give exactly the same result for "fresh install" and "denied twice". Without the flag a fresh install already shows Open app settings. iOS has .notDetermined so it doesn't need one. - Ref: shouldShowRequestPermissionRationale

    registerForActivityResult lives in the Activity - What: registers the launchers for requesting permissions / enabling Bluetooth. - Why: they must be registered before the Activity is STARTED; calling it in a Composable/on a button tap throws IllegalStateException. - Ref: Activity Result APIs

    BluetoothService.readiness() — a pure function combining permissions + radio - What: returns one single answer can we scan yet / what's blocking. - Why: with permissions but the radio off, scanning returns 0 devices without an error. 2 screens share 1 function → no screen guesses differently. - Ref: Set up Bluetooth · CBManagerState

    BroadcastReceiver(ACTION_STATE_CHANGED) 🤖 / delegate centralManagerDidUpdateState 🍎 - What: know immediately when the user toggles Bluetooth. - Why: pulling down Quick Settings doesn't take the Activity through onResume → without listening the screen is wrong. Register in onStart, unregister in onStop, or it leaks. - Ref: BluetoothAdapter.ACTION_STATE_CHANGED

    StateFlow 🤖 / @Observable 🍎 in BluetoothClientService - What: the service holds state (devices, isScanning, connection), the screen collectAsState() / reads the property and redraws by itself. - Why: Android BLE callbacks run on a Binder thread — writing a plain variable that Compose reads is a cross-thread access. iOS uses queue: nil so the delegate is already on main. - Ref: StateFlow · Observation

    10 s scan timeout + dedupe by id - What: stopScan by itself after 10 s; a Map id → device overwritten on every packet. - Why: every advertising packet = 1 callback (dozens per second). An endless scan drains the battery + Android silently blocks you when you start too often. - Ref: Find BLE devices · scanForPeripherals

    connectGatt(..., autoConnect=false, ..., TRANSPORT_LE) + always close() 🤖 - What: connect right away over BLE; close GATT on disconnect. - Why: without TRANSPORT_LE dual-mode devices may go over Classic by mistake → 133. No close() → leaked client slots, after ~30 times every connect returns 133. - Ref: Connect to a GATT server

    Keep a strong ref to CBPeripheral + your own 15 s timeout 🍎 - What: store the peripheral in a dictionary before connect; schedule a 15 s Task.sleep then cancelPeripheralConnection. - Why: CoreBluetooth holds it weakly → when the peripheral is released the connection is cancelled silently; iOS connect never times out by itself. - Ref: connect(_:options:)

    scannerButtonsOf() / isDeviceShown() — screen rules are pure functions, not inside the Composable/View - What: scannerButtonsOf takes (selected?, connectable?, is it the connected device?, state, ready) and returns Connect enabled/disabled/spinner + Disconnect enabled/disabled; isDeviceShown decides which rows show based on the Device Name box + the 2 switches. - Why: many combinations make it easy to miss a case (e.g. right after Error Connect must work again; the connected device must never be hidden by a switch). Inside the UI it can only be checked by hand on a device; split out, the unit tests run in 1 second, and both platforms share the same cases. - Ref: Android — Guide to app architecture (UI layer) · Swift Testing

    Ignore callbacks from the OLD connection when switching devices - What: connected to A, select B and tap Connect → A is dropped; a late "A disconnected" callback is ignored (🤖 g !== gatt · 🍎 compare peripheral.identifier). - Why: BLE callbacks arrive asynchronously. Without filtering, "A disconnected" arrives while B is Connecting… → the card flips to Disconnected, row B loses its spinner even though B is still connecting. - Ref: BluetoothGattCallback.onConnectionStateChange · didDisconnectPeripheral

    The list keeps first-seen order, not sorted by RSSI - What: new rows are appended at the end; RSSI updates in place. - Why: tapping a row = selecting the device to Connect, so rows must not move — RSSI changes several times a second, sorting by signal means your finger lands on another device.

    The screen's "clock": LaunchedEffect + delay(1000) 🤖 / TimelineView(.periodic) 🍎 - What: redraw every second so "Last seen: 3s ago" counts by itself and cards fade on their own. - Why: the UI only redraws when state changes. A silent device = no new packets = no new state → without a clock the card never fades when it should. - Ref: LaunchedEffect · TimelineView

    The gattOps GATT queue (🤖 only) — Day 3 - What: each read / CCCD write is one GattOp; the next op only runs when the previous op's callback arrives (opDone()). - Why: the Android Bluetooth stack runs one GATT op at a time. Calling readCharacteristic while a descriptor write is in flight → returns false, the op is lost, no callback at all → the UI waits forever. CoreBluetooth queues by itself so 🍎 doesn't need it. - Ref: BluetoothGatt.readCharacteristic · Punch Through — Android BLE guide (operation queue)

    Properties are a bitmask, GattProperties.of(raw) — Day 3 - What: 1 byte declared by the peripheral → 5 flags READ / WRITE / WRITE NO RESP / NOTIFY / INDICATE → decide which buttons show. - Why: Android's PROPERTY_* and iOS's CBCharacteristicProperties are the same bit values from the spec → 1 function, 1 test suite for both platforms. Showing a Read button for a non-READ characteristic = an error on tap. - Ref: BluetoothGattCharacteristic.PROPERTY_READ · CBCharacteristicProperties

    Little-endian + decode by UUID — Day 3 - What: decode(uuid, bytes) — known UUID → per spec (battery %, UTF-8 strings, heart rate), unknown → ASCII / uint LE / hex only. - Why: BLE sends the low byte first: 34 12 = 0x1234 = 4660. Reading it backwards as 13330 is the most common hand-decoding bug. Kotlin's Byte is signed → always and 0xFF. - Ref: Bluetooth SIG — Assigned Numbers / GATT Specification Supplement

    Read and notify arrive on the same callback (🍎) — Day 3–4 - What: pendingReads remembers the key just readValued; didUpdateValueFor with that key → READ, without → NOTIFY. - Why: CoreBluetooth doesn't say whether a value arrived because we asked or because the peripheral pushed. Android splits it into 2 callbacks (onCharacteristicRead / onCharacteristicChanged). - Ref: peripheral(_:didUpdateValueFor:error:)

    CCCD 2902 — Day 4 - What: the "switch" descriptor on the peripheral; write 01 00 = notify on, 02 00 = indicate on, 00 00 = off. - Why: the peripheral pushes nothing until someone enables the CCCD. 🤖 must do 2 steps itself (setCharacteristicNotification + write CCCD), missing either is silent with no error. 🍎 setNotifyValue does both. - Ref: Android — Receive GATT notifications · setNotifyValue(_:for:)

    API 33 callbacks (🤖) — override both the new and the old version — Day 3–4 - What: onCharacteristicRead(…, value, status) / onCharacteristicChanged(…, value) for API 33+; the old ones read c.value + copyOf() for API 26–32 (the old ones guard SDK_INT >= 33 → return). - Why: minSdk 26. Writing only the new version → Android 12 and below never get data. The old version uses one shared buffer c.value → the next notify packet overwrites the previous one unless copied immediately. - Ref: BluetoothGattCallback.onCharacteristicChanged

    clearGattState() on every disconnect path + keep the log — Day 4 - What: manual disconnect, signal lost, radio off, device switch, connect fail all call one function that clears services + the queue + pending CCCD writes. received / lastRead are kept until Connect to a new device or Clear. - Why: characteristic objects die with the connection — keeping them means tapping Read on a dead object. The log is kept because it's exactly what you need to read after "killing the peripheral" to know what the last packet was.

    appendCapped(…, 50) — Day 4 - What: append the new line at the end, drop the oldest when over 50. - Why: notify can be hundreds of packets/second (ESP32 BLE_notify); an unbounded list → memory + draw time grow forever, the screen freezes after a few minutes.

    BluetoothConnectionState is a sealed interface / an enum with associated values - What: 5 states, Connected carries the name, Error carries the reason. - Why: exhaustive when / switch — add a state and forget to draw it in the UI → build error, not a runtime bug. Disconnected (we tapped, grey) is separate from Error (dropped, red). - Ref: Sealed classes · Swift enums

    Write with response / without response — task 004 - What: planWrite picks the type from the properties: has WRITE → with response, only WRITE NO RESP → without response. - Why: with response = the peripheral sends an ACK → you know for sure it arrived, errors (e.g. not writable) come back for real. Without response is faster but "fire and forget": 🍎 no callback, 🤖 the callback only means it was sent. 🍎 writing with the wrong type for the properties silently drops the write. - Ref: BluetoothGatt.writeCharacteristic · CBCharacteristicWriteType

    fromHex / fromText + the \r escape — task 004 - What: convert typed text into bytes. Hex accepts 41 54, 4154, 0x41,0x54; Text turns \r \n \t \\ into the real characters. - Why: the input box can't type Enter as 0x0D, yet ELM327 only runs a command when it sees \r. Many hex styles are accepted because people copy from nRF / Logcat / docs. Pure functions → the same test cases on both sides. - Ref: ELM327 datasheet — AT commands

    MTU = the max ATT packet, data = MTU − 3 — task 004 - What: 🤖 requestMtu(247) through the queue after discovery, the real value arrives in onMtuChanged; 🍎 reads maximumWriteValueLength(for: .withoutResponse). The UI shows MTU · max bytes and blocks longer payloads. - Why: the default 23 → only 20 data bytes per packet (3 bytes opcode + handle). Longer notify / write packets get truncated or rejected (status=13 INVALID_ATTRIBUTE_LENGTH). The MTU belongs to one connection → back to 23 after a disconnect. - Ref: BluetoothGatt.requestMtu · maximumWriteValueLength(for:) · Punch Through — Maximizing BLE throughput
